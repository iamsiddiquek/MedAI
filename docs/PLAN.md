architecture sections are replaced by [ARCHITECTURE.md](ARCHITECTURE.md), as requested.

## 1. What we are building

Afia is a UAE-first ambient clinical documentation platform. A clinician asks the patient for
consent, records the consultation, and receives a draft note in which every line points at the
part of the conversation it came from. The clinician corrects it and signs it. Only then is it
a clinical record, and only then may it go to the hospital's record system.

Four promises hold everywhere, from the first line of code:

1. Software drafts; the clinician decides. Nothing becomes final without a clinician's signature.
2. One organisation never sees another's data.
3. Every model call goes through one governed gateway that can be switched off per tenant or globally, and that respects where data may be processed.
4. Every action that matters leaves evidence that cannot be quietly changed.

Afia is not a hospital information system. Scheduling, orders, laboratory, pharmacy and
general ledger stay in the hospital's own systems and are integrated, not rebuilt.

## 3. Decisions taken

Your three answers:

| Question | Decision |
|---|---|
| Where to build | A brand-new repository (this one). The old 14-service build is not reused. |
| How many services in Phase 0 | Five deployables: `web`, `api-gateway`, `core`, `model-gateway`, `ambient-ai` |
| AI engines for the first runnable build | Local open-source: Whisper for speech-to-text, an Ollama model for drafting, both behind a LiteLLM router. Tests use synthetic models. |

Decisions I made within those answers (each is an ADR in `docs/adr/README.md`; say if you
want any of them changed):

- The clinical modules live in one Spring Boot application with one database schema each and a test that fails the build if a module touches another module's schema.
- Plain SQL through Spring's JdbcClient with Flyway migrations, not an ORM: the invariants (tenant filter, guarded state transitions, immutability) are visible in every statement.
- Users, roles and the tenant attribute live in Keycloak for now. Tenant administration screens come in Phase 2.
- One Kafka topic for encounter events, with a dead-letter topic. No schema registry, Redis, workflow engine or search engine until a real need appears.
- A real recording never falls back to a synthetic model. If local models are down, the clinician writes the note by hand.
- Whisper does not separate speakers. Transcripts from the local route show "Speaker"; diarization is its own evaluated piece of work in Phase 3.

## 4. The architecture in one paragraph

The web app talks only to the gateway. The gateway checks the token and forwards `/api` calls
to `core`, which owns every clinical record in PostgreSQL and stores audio in object storage.
When a recording is complete, `core` commits an event with the state change; a relay publishes
it to Kafka. `ambient-ai` picks it up, fetches the audio, asks `model-gateway` for a transcript
and then for a draft, checks each draft line against the transcript, and hands both back to
`core` through an internal API. `model-gateway` is the only thing that can reach a model.
Details, diagrams and the list of enforced rules are in [ARCHITECTURE.md](ARCHITECTURE.md).

## 5. Delivery phases

Each phase ends at a gate. Work on the next phase's critical path does not start until the
gate passes. Phases map to the blueprint's roadmap as shown.

### Phase 0: golden path skeleton (this delivery)

Goal: record -> transcribe -> draft -> review -> sign, with consent, tenant isolation, audit,
provenance and the no-AI fallback, across web, gateway, core, model-gateway and ambient-ai.

Built: everything in section 7. Blueprint items: WBS 1.1 and 1.2, most FR rows, gates G1 and G2
in code.

Gate P0: the stack starts from `compose.yaml` on your machine, CI is green, and one synthetic
consultation goes from recording to a signed note through the web app. **Not yet passed**: the
Java services have not been compiled or run (section 8).

### Phase 1: make it provable (about 3 to 4 weeks)

1. Get CI green; fix whatever the first compile and Testcontainers run finds.
2. Bring up the compose stack; fix image tags and wiring found on first start.
3. Browser end-to-end test (Playwright) of the golden path and the main refusals.
4. Integration tests against real Kafka and MinIO (publish, consume, duplicate, retry, dead letter, replay).
5. Persist model-gateway policy and execution ledger in PostgreSQL (its own database).
6. OpenTelemetry traces across web call -> core -> Kafka -> ambient-ai -> model-gateway, checked for clinical content.
7. Secrets from a secret manager; multi-factor sign-in; gateway rate limiting.
8. Backup and restore drill with written evidence.
9. Resumable chunked audio upload; clean-up of unreferenced audio.

Gate P1 (blueprint G13, G17, A1): real infrastructure proves publish, consume, duplicates,
retry, replay, isolation and recovery; a new engineer reproduces build and golden path.

### Phase 2: platform hardening (about 6 to 8 weeks)

- Integration module: FHIR export of the signed note with retry, dead letter, reconciliation; export failure never touches sign-off (WBS 2.2, G5 against a FHIR sandbox).
- Document module: upload, checksum, malware scan, versions, signed retrieval, retention (WBS 8, G14).
- Notification module: in-app inbox and email, templates in Arabic and English, no clinical content in subjects (WBS 9, G15).
- Signed-note amendment, co-signature, break-glass access.
- Tenant administration: users, roles, AI toggles and residency policy from the web app.
- Practitioner module: licence, specialty, privileges.
- Retention schedules, legal hold, deletion across database and object storage.

### Phase 3: clinical quality and Arabic (about 8 weeks)

- Evaluation harness: word error rate, speaker error, unsupported statements, omissions, negation and medication errors, edit burden, latency, cost (WBS 1.3, G3).
- Governed AI data plane: dataset registry, clinician feedback capture, release approval records; separate storage and credentials (blueprint section 10, G16).
- Diarization; Arabic, Gulf dialect and code-switching benchmark by specialty and room acoustics (WBS 2.1, G4).
- Terminology service and bilingual dictionaries; note templates by specialty.

### Phase 4: UAE pilot readiness and pilot (about 3 months)

- One production EHR adapter chosen with the pilot provider.
- Compliance pack: data flows, threat model, safety case, incident process, exit plan; DHA, DoH and MOHAP mapping (WBS 2.3, G6).
- Deployment profiles: UAE cloud, private or hybrid, local models. High availability, disaster recovery, runbooks, dashboards and alerts (WBS 3.2, G8).
- Tenant onboarding and go-live workflow; vendor, licence and model-rights registers.
- Controlled pilot with one provider, one specialty, measured against a baseline (WBS 3.1, G7).

### Phase 5: workflow intelligence (about 2 months)

Patient summaries and instructions, follow-up drafts, task suggestions, referral drafts, coding
suggestions, structured medications, allergies and diagnoses. Everything stays a suggestion
until a person confirms it, with evidence links (WBS 4.1, G10).

### Phase 6: enterprise and region (customer-driven)

Second-organisation onboarding by configuration (G9), tenant exit and export, bounded agents
with approval gates (G11), country profiles for Saudi Arabia, Qatar, Bahrain and Oman (G12),
and, only where a customer case justifies it, patient billing, SaaS metering, patient portal
and scheduling.

## 8. What is verified and what is not

See [CURRENT_STATE.md](CURRENT_STATE.md) for commands and results. In short:

- **Run and passing here:** model-gateway (24 tests), ambient-ai (13 tests), both lint clean; web typecheck, lint, 11 tests and production build.
- **Written, syntax-checked, not compiled or run:** `core` and `api-gateway`. The build machine could not download Java dependencies and has no Docker, so no Java test has executed. Expect some compile or wiring fixes on the first CI run.
- **Written, not run:** `compose.yaml`, Dockerfiles, Keycloak realm, LiteLLM config, CI workflow. Image tags for MinIO, Speaches, LiteLLM and Ollama are from memory and need checking.
- **Not done at all:** a full run through the browser, real microphone capture against the backend, any clinical evaluation of Whisper or the Ollama model, Arabic text review by a native clinician, legal review of the consent wording.

By the blueprint's own rule, nothing here may be called production-ready.

## 11. Risks

| Risk | Effect | Response |
|---|---|---|
| Java code has never been compiled | Phase 0 gate may slip by days | First task of Phase 1; CI is the judge |
| Local models are slow on a laptop | A ten-minute consultation may take many minutes to draft | Timeouts are generous; measure in Phase 1; GPU or smaller models |
| Local model quality for Arabic and Gulf dialect is unknown | Poor drafts, clinician distrust | Evaluation harness before any pilot claim |
| No diarization | Draft cannot tell who said what | Phase 3; until then the model infers from content, and the clinician reviews |
| Whole-file upload | A closed tab loses the recording | Resumable upload in Phase 1; the active recording can already be resumed with a file |
| Single database for all modules | A noisy module affects sign-off | Schema boundaries allow extraction; measure before splitting |
| Scope pull from the 273-feature catalogue | Golden path never hardens | The register's phase column and the gate rule; one slice at a time |
